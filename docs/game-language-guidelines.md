# 小游戏平台 · 游戏语言规范

> 适用范围：游戏厅公共界面 + 全部机台（稿纸 / 抽词 / 砖块 / 叠山 / 敲印 / 破砖 / 走墨 / 垒塔 / 墨潮 / 纸上军团）。
> 配套文档：[game-terminology-glossary.md](./game-terminology-glossary.md)（逐游戏术语表，含数值与出现位置）。
> 本规范只管「玩家读到的字」，不改任何游戏机制、数值、触发条件与奖励规则。

## 核心原则

游戏可以有自己的文化、特色和创意，但不能让玩家为了理解一个功能而学习一套陌生的词汇。

1. **功能描述必须通俗。** 玩家读完一句话，应当立刻知道它代表什么功能，不需要猜。
2. **特色名称与功能解释分离。** 允许保留世界观命名，但特色名称不能代替功能说明。
   推荐格式：`特色名称 · 通俗解释`，例如「横锋 · 横扫整行」「墨魂 · 抵挡一次致命伤害」。
   特色名称没有必要时，直接用通俗名称，不为形式强行保留。
3. **按钮必须明确表达动作。** 玩家一眼知道点击后会发生什么：开始游戏 / 再来一局 / 继续 / 返回游戏厅。
4. **技能与机制必须说明实际效果。** 说清楚：能做什么、什么条件触发、影响谁、持续多久、数值多少。
   所有数值必须与代码一致，动态数值必须与真实状态一致。
5. **每款游戏保留自己的风格。** 统一的是「表达标准」，不是词汇本身。不同游戏不强行共用同一套词。

## 分场景表达标准

| 场景 | 标准 | 反例 → 正例 |
| --- | --- | --- |
| 操作按钮 | 短、直接、动词明确 | 「走了」→「离开商店」；「回到开头」→「返回主菜单」 |
| 规则说明 | 简单、准确、循序渐进；开局只给一句话核心玩法 | 一次性长文档 → 开局一句 + 常驻提示行 + 随时可查的帮助 |
| 技能描述 | 突出触发条件与实际效果，数值与代码一致 | 「压制笔势」→「贴近阵线后暂停该线合击，击败它立刻恢复」 |
| 状态反馈 | 明确告诉玩家发生了什么 | 「林中的东西接受了你」→「迎击生效 · 下波精英更多」 |
| 错误提示 | 解释原因 + 怎么办 | 「招不动了」→「军粮不足，无法继续招募」 |
| 奖励说明 | 突出获得内容和实际用途 | 「获得灵韵加成」→「墨屑已存入墨库 · 可换永久强化」 |
| 失败提示 | 说明失败原因，暗示可以再试 | 「堆满了」→「字堆到顶线了」 |
| 世界观氛围 | 允许艺术性，但不能代替功能说明 | 印章、阶段名、Boss 登场词可保留文学性 |

## 平台级公共约定

- **计量单位面向玩家**：不用 `px`、`帧`、`budget` 等开发者单位。偏差用「偏左 / 偏右」，
  距离用「格」，时间用「秒 / 分钟」。
- **计步统一叫「步」**，不叫「手」（围棋术语对普通玩家是生僻词）。
- **关卡统一叫「关」**，不叫「段」；无尽模式的阶段名（如「初落笔」「血染长坡」）
  只作氛围标签，旁边必须有波次 / 时间等可读数值。
- **货币命名各游戏独立，但游戏内部必须唯一且一致**：
  - 墨潮：局内「铜钱」，局外「墨屑」。禁止同一货币混用 金 / 金币 / 墨钱 / 铜钱。
  - 纸上军团：局内「军粮」「银币」，局外「金币」「材料」「英雄碎片」。
    「金铢」是生僻词，显示层统一为「金币」（存档键 `gold` 不变）。
- **相同含义不跨游戏强行统一**：墨潮的「墨屑」与军团的「金币」都是局外货币，
  各自保留世界观名称，但各自游戏内只允许一个叫法。
- **缩写只允许出现在空间极小且已有全称锚点的地方**（HUD 图标「粮 / 银 / 斩」），
  且必须带 `title` 全称解释。结算、商店、帮助等阅读场景一律用全称。

## 新手理解体验

- 开局卡片只放**一句核心玩法**；补充规则放第二行短句，不超过两行。
- 关键机制在**首次出现时**给一条短提示（首次金印、首次连锁砖、首次高墙……），
  每局每类只提示一次，不弹窗、不打断操作。
- 游戏过程中底部常驻一行操作提示（`g-hint`），玩家随时能看到「现在该做什么」。
- 复杂游戏（墨潮 / 纸上军团）提供随时可打开的帮助 / 玩法说明入口。
- 失败结算必须说明原因；奖励结算必须说明用途。

## 技术红线（改文案时严禁触碰）

平台架构：React 外壳（`Hall.tsx`）+ 独立 TypeScript 游戏模块 + DOM / Canvas 2D。

1. 只改**玩家可见的显示字符串**。不改：
   - 内部变量名、类型名、枚举值（如 `UnitKind`、`EnemyKind`、`BossId`）；
   - `localStorage` 存档键与存档结构（`txxt.*`、`legion.*`、`rogue.*`）；
   - 事件标识 / `data-act` / `data-id` / DOM id（探针与自动化依赖它们）；
   - 成绩记录字段、配置表 `id`。
2. 改任何数值描述前，先读对应逻辑代码核对（倍率、秒数、数量、触发条件）。
3. 不为改文案重构游戏逻辑。唯一例外：发现「显示内容与真实效果不符」的缺陷
   （如事件选项展示与实际生效不一致），做最小修复使两者一致，并在术语表中记录。
4. 改完必须 `npm run build`（tsc 严格检查 + vite 构建）通过，
   并实际运行检查动态提示、文字溢出 / 截断、存档兼容。
5. 截图等过程产物放 `site/.qa/`，保留 7 天，不入库（见 AGENTS.md）。

## 验收标准（第一次接触的普通玩家视角）

- 看见按钮就知道能做什么。
- 看见技能就知道有什么效果。
- 看见规则就能理解基本玩法。
- 遇到错误就知道原因和解决办法。
- 获得奖励就知道用途。
- 不需要专门学习自创词汇，不需要反复阅读长篇说明。
